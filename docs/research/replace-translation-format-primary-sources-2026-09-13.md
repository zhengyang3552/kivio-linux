## 研究结论

当前问题横跨信息表达、分组与容器、排版策略、绘制和验收，并非一个字体系数造成。最明确的发现是：单行约束没有传到最终排版函数；字号可以持续缩小；样式和真实基线信息不足；固定画布字号上限不随显示比例变化；测试把“完整且不越界”与“保留格式”混在了一起。

下午的修改确实会在部分构造行框中进一步缩小字号，但它同时修正了越界判断；其余多项结构问题在修改前已经存在。因此，现有证据不支持简单认定“整次修改都错了”，也不支持直接回滚或换一个模型就能解决。

用户已明确使用场景以英译中为主，实际很少遇到译文放不下；确有需要时可以牺牲一些字号。因此，后续重点是正常长度的英译中结果为什么仍会变小、错位或错误换行，允许必要的小幅缩字，不把极端长译文当作主要设计场景。缩字的具体幅度尚未标定，不等于允许持续缩到不可读。

本文后半部分列出了本地源码证据、可重复实验、测试盲区和后续讨论选项；所有数值都标明是否来自简化构造实验，没有将其当作真实截图的测量结果。长译文实验用于暴露算法约束缺失，不代表用户日常场景的发生频率。

## 1. 外部一手资料：格式为什么不能简化成“塞进矩形”

### 1.1 Canvas：墨迹边界、字体度量和排版行框有不同职责

**规范事实。** `TextMetrics.actualBoundingBoxAscent/Descent` 描述当前字符串相对所选基线的墨迹边界；同一字体、同一字号，不同字符的值也会变化。`fontBoundingBoxAscent/Descent` 对应字体度量；规范特别区分“为具体文字画边界”和“背景高度不随文字内容变化”的用途。`width` 是排版 advance，倾斜字形的实际水平墨迹范围可能更宽。[WHATWG TextMetrics](https://html.spec.whatwg.org/multipage/canvas.html#textmetrics)

**对本项目的推论。** 实际墨迹适合检查是否被切掉，但不能直接代替所有行的稳定行距，也不能把 OCR 墨迹高当作完整 em 框高度。应分别保存源文墨迹范围、估计字号、基线位置、行间 advance 和译文墨迹范围；同级文字优先共享字号与基线/行距规则。对一行 `ooo` 和一行 `Ágj`，不能因为墨迹高度不同就默认它们属于不同字号。该建议需要源截图标注验证，并非规范提供了字号反推算法。

**规范事实。** Canvas 文本准备算法形成无限宽的单行盒；ASCII 空白会替换为空格。传入 `fillText` 的 `maxWidth` 后，浏览器可选择更窄的字体、水平压缩或更小字号，直到满足宽度。[WHATWG 文本准备算法](https://html.spec.whatwg.org/multipage/canvas.html#text-preparation-algorithm)

**推论。** 多行断行、基线间距和无法容纳时的策略需要应用明确管理；仅使用 `maxWidth` 无法保证字号、字形比例和层级保真。一个排版结果应统一供测量、绘制和溢出判断消费，避免分别计算后出现坐标偏差。

### 1.2 CSS Text：单行是约束，语言断行是规则，溢出是另一件事

**规范事实。** `white-space: nowrap` 禁止软换行；`pre` 保留强制换行但不允许软换行；`normal` 和 `pre-wrap` 才允许按规则软换行。`word-break`、`line-break`、`overflow-wrap` 各有职责。CSS 使用扩展字素簇作为排版字符单元的基础，并允许针对文字系统调整，不能把每个 Unicode 码点都当作可独立拆开的字。[W3C CSS Text 3：空白与换行](https://www.w3.org/TR/css-text-3/#white-space-property)、[断行](https://www.w3.org/TR/css-text-3/#line-breaking)、[字符单元](https://www.w3.org/TR/css-text-3/#characters)

**对本项目的推论。** 单行菜单、按钮或表格字段应向最终排版器传递明确的单行约束，不能只留下高度。段落需要语言相关断行；中文标点、组合附标、emoji 和英文长词不能仅靠逐码点或空格切割处理。DOM/CSS 可以提供现成断行行为，但不会自动识别截图里的容器、字号或原字体，所以更换渲染介质不是完整修复。

### 1.3 Nimbus：同级字号需要跨块关系，初始字号统一还不够

核验提交：[`3e7529aadde5f2ce2ac0764f1104e4eb0627c3b0`](https://github.com/nimbus-translate/screen-translator/tree/3e7529aadde5f2ce2ac0764f1104e4eb0627c3b0)。

**源码事实。** 它先按顶边接近、背景明暗和高度比组织同排元素，再按高度组织其余文字，以组内中位源行高估计字号。绘制时明确区分单行垂直居中与多行顶部对齐。该关系建模比每块独立按 OCR 高度定字号更接近 UI 层级，但这仍是几何启发式。[字号组](https://github.com/nimbus-translate/screen-translator/blob/3e7529aadde5f2ce2ac0764f1104e4eb0627c3b0/ui/translation_overlay.py#L100)、[单行/多行绘制](https://github.com/nimbus-translate/screen-translator/blob/3e7529aadde5f2ce2ac0764f1104e4eb0627c3b0/ui/translation_overlay.py#L399)

**源码限制。** `_fit_font` 仍逐块缩小字号；单行到了最小字号可忽略宽度不满足，多行失败也仍返回字体，绘制端再裁切。注释说用横向压缩消化译文增长，实际这一路没有设置 stretch。因此不能据此宣称最终同级字号一致或全文完整。[适配循环与字体创建](https://github.com/nimbus-translate/screen-translator/blob/3e7529aadde5f2ce2ac0764f1104e4eb0627c3b0/ui/translation_overlay.py#L427)

**推论与部署边界。** 借鉴“同一导航栏/表格行的文字相关联”，但应分别评估源样式分组和最终渲染一致性。Qt point size、逻辑像素与本项目 Canvas CSS 像素并非可直接替换的数值，不应照搬字号系数。这次未运行 Nimbus，未验证其 DPI 下的实际表现。

### 1.4 BallonsTranslator：样式、段落与墨迹是显式数据，不是最后补丁

核验提交：[`84ba500ea1a4f523ca79f1c77d8c642eea3d1d07`](https://github.com/dmMaze/BallonsTranslator/tree/84ba500ea1a4f523ca79f1c77d8c642eea3d1d07)。

**源码事实。** `FontFormat` 显式包含字体家族、字号、字重、斜体、下划线、对齐、书写方向、行间距和字间距等字段。具备这些字段证明可以表示和编辑样式，并不能证明它们都由截图自动准确识别。[样式结构](https://github.com/dmMaze/BallonsTranslator/blob/84ba500ea1a4f523ca79f1c77d8c642eea3d1d07/ballontranslator/utils/fontformat.py#L657)

**官方架构说明。** 范围内字体样式与段落行距由 `QTextDocument` 格式拥有；排版位置、墨迹边界与缓存由同一次完成的 layout 派生，绘制和几何使用同一结果。横排保留 Qt shaping 与词边界断行；首行不加前置行距，后续行使用目的段落的间距规则。[官方 text layout 文档](https://github.com/dmMaze/BallonsTranslator/blob/84ba500ea1a4f523ca79f1c77d8c642eea3d1d07/doc/ui/text_layout.md)

**源码事实。** 自动布局工具的输入包含 mask、单词宽度、行高、间距和是否参考源行宽度，体现“可排区域”和“源行关系”参与排版。[自动布局输入](https://github.com/dmMaze/BallonsTranslator/blob/84ba500ea1a4f523ca79f1c77d8c642eea3d1d07/ballontranslator/utils/text_layout.py#L341)

**对本项目的推论。** 需要先决定样式信息如何进入数据模型，再讨论还原字重或行距；渲染器无法恢复上游根本没传下来的信息。首阶段可以先保存粗体/常规、字号层级和对齐等有限信息及其置信度，低置信度使用一致的目标语言字体。Qt 富文本编辑器和漫画气泡布局不适合直接移植进轻量截图覆盖层；这里借鉴职责划分，不推荐照搬完整引擎。

### 1.5 PP-StructureV3：结构识别有价值，但文档结构不等于桌面 UI 结构

**官方接口事实。** 输出中 `parsing_res_list` 含区域框、类型、内容和阅读顺序；表格输出另含 `cell_box_list`、`pred_html` 和单元格 OCR。这说明文本行之外可以保留“属于哪个区域/单元格”的信息。所列接口并未提供原字体家族、字重、基线恢复承诺。[官方结果结构](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PP-StructureV3.html#22-python-script-integration)

**官方适用域与部署事实。** 官方列出的布局类别和训练数据主要面向论文、PPT、杂志、合同、书籍等文档；管线由布局、OCR、可选表格等模块组成，支持设备配置。文档里的模块耗时与指标属于其指定条件，不能推算为本机整屏替换延迟，也不能证明能准确识别菜单和按钮。[官方模块、模型及基准说明](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PP-StructureV3.html)

**推论。** 表格/文档场景可以评估结构模型是否减少跨栏和跨单元格合并；桌面 UI 应先验证容器识别准确率、模型包体和端到端耗时，不能直接以它替换现有 OCR 并期待格式自动恢复。此次没有下载或运行模型。

## 2. 从外部证据推导的设计选项（尚未实施）

### 2.1 先约定格式保留的优先级

设译文在原字号、允许行数和固定容器中所需空间大于可用空间，则无法同时保留完整内容、原字号、原行数与原边界。这是固定约束的可行性冲突；不断缩字只是选择牺牲其中一项，并非“自动恢复格式”。建议讨论以下行为，而不是继续调单个缩字系数：

| 场景 | 优先保留 | 可以考虑的容纳策略 | 应明确报出的失败 |
| --- | --- | --- | --- |
| 菜单、按钮、标签 | 单行、同级字号、基线、容器 | 在容器剩余空白内扩展；在可读范围内有限缩字；经语义检查的简短译法 | 无法满足最小可读字号与单行约束 |
| 正文段落 | 阅读顺序、段落宽度、字号层级、稳定行距 | 在所属段落内部重新断行；仅使用确认的空白区域增高 | 溢出容器、侵入下一段或被截断 |
| 表格 | 列归属、单元格边界、数值对应关系 | 单元格内按原规则断行；同列/同行协调字号 | 跨格、错列、覆盖边框或数字含义改变 |
| 标题 | 与正文的大小/粗细关系、对齐 | 使用标题容器空间；有限调整后报告降级 | 标题缩到与正文同级或更小 |

这些是待讨论的产品策略，并不是外部规范规定的默认值。简短译法需要翻译语义检查，不能删除数字、否定、限定条件来获得视觉适配。无法容纳时是否允许点开完整译文、旁置译文或保留原文，需单独定产品行为。

### 2.2 将“观测值、样式估计、容器约束、排版结果”分开

建议研究数据至少能区分以下四层，避免一个 `height` 同时承担全部职责：

1. **观测值：** OCR 行框、文字、旋转、置信度、截图坐标与缩放关系；若有可靠像素分析则记录墨迹范围。
2. **样式估计：** 源字号层级、粗体/常规、字色、对齐、基线/行距估计；保留来源与置信度。完整字体家族识别应单独验证，不能把目标字体回退当成源字体识别。
3. **容器约束：** 单行/段落/单元格、可排矩形、邻接保护区、允许行数、样式组关系。
4. **排版结果：** 最终字体及字号、每行文本和基线、实际墨迹范围、缩字比例、是否完整、违反哪项约束。最终测量与绘制消费同一个结果。

该拆分综合了 Canvas 的度量区分、CSS 的断行约束、Nimbus 的跨块样式关系、BallonsTranslator 的统一 layout，以及 PP-Structure 的区域/单元格信息。它是本次工程推论，不要求一次性接入新的大模型或重写所有模块。

### 2.3 研究阶段的验证边界

本轮外部结论可信到“规范语义/当前核验源码行为”为止，未比较任何外部项目的视觉质量、速度或部署稳定性。下一轮如验证实现方案，应把 OCR/分组错误、样式估计错误、容纳策略降级与绘制错误分别归因；仅检查文字不越界，会把过度缩小、层级损坏和错误断行误判为成功。真实截图与固定译文可先用于离线排版对比，减少实时模型输出变化对结论的干扰。

## 基于证据的方案取舍，供讨论而非实施决定

### 已明确的场景与取舍

翻译可能增长，字形宽度和行高也会变化，字符数不是空间预算。[W3C：翻译后的文字尺寸](https://www.w3.org/International/articles/article-text-size)

工程推论：当译文在指定字号下确实放不进固定容器时，“全文完整、原字号、原行数、原容器”不能全部满足。用户已选择必要时允许牺牲一些字号。这是少见情况的容纳策略；本轮调查不能用它解释所有正常英译中样本的格式问题。

据此，建议先验证普通菜单、按钮和表格的容器、单行限制与同级字体层级，以及正文的位置、行距和对齐。可容纳时应保持稳定字号，确实受空间限制时允许有限缩小。正文重排方式仍待讨论；局部展开或旁置译文仅保留为备选，不是已确认的产品需求，也不应成为当前修复的前置条件。本文不设未经验证的缩字百分比或8px/10px等硬阈值。

| 路线 | 能解决的部分 | 代价与局限 | 当前判断 |
| --- | --- | --- | --- |
| 有边界地修正现有 Canvas 路径 | 单行约束、DPI单位、同级字号、稳定基线、语言断行和溢出状态 | 仍不能凭空恢复未采集的字体样式、真实容器或复杂背景 | 适合先作为普通桌面UI的候选，需固定样本比较 |
| 增强版面和样式描述，再按区域类型排版 | 区分语义组、擦除区、真实容器、源行、样式层级；减少混用一个框引发的问题 | 必须确认这些信息怎样可靠取得，推断错误可能比缺少信息更糟 | 是较完整的设计方向，不等于本次授权重构 |
| 使用浏览器原生段落排版作为局部候选 | 利用语言断行、双向文字、行内样式和文本布局能力 | 不会恢复OCR没有的样式；离散行槽、导出合成和两平台一致性仍需验证 | 应与Canvas做小范围同样本对照，不直接决定整层替换 |
| 引入额外版面模型或背景修复模型 | 前者可能帮助文档结构；后者可能改善复杂背景 | 无法代替单行、字号、基线和溢出策略；有部署、延迟和质量评估成本 | 不能把换模型当本轮排版问题的统一解法 |

上述均为本地与外部证据综合后的工程判断，没有外部项目在本机的性能/质量排名，也没有“装上某个模型即可解决”的结论。

### 后续评估怎样才有说服力

建议先固定少量真实问题截图及允许保存的脱敏等价样本，分别覆盖：同级菜单、居中标题与粗体、密集多行正文、多列/表格、图标相邻的深色卡片、渐变/照片文字、中英混排与标点，以及相同逻辑界面的1×/1.25×/2×截图。真实截图暂未提供，当前无法判断各类问题在用户日常场景中的占比。

每个样本分两种运行：固定 OCR 和译文，仅比较排版/擦除；再跑真实 OCR 和真实翻译检查全链路。先保留原图、OCR叶子、翻译分组、容器/行槽、擦除覆盖、清理图、译文与最终合成图，失败才可以归因到具体层。

建议把验收拆成以下独立项；数值阈值待样本标定，不能以“像素不越界”代替全部指标：

- 内容：译文对应关系、遗漏/截断、复制全文是否一致。
- 可读性：最终显示字号及相对源字号比例、同级字号差异、真正无法容纳的区域占比。
- 格式：单行是否仍单行、容器越界/相邻元素覆盖、基线与首行位置、稳定行距、对齐、中文标点与字素完整性。
- 背景：原字残留与非文字区域损坏分别统计，不能仅比较填充结果自己的行中位色。
- 平台：在实际 WebView 和显示比例下看合成图；fixture 中写了平台名不算跨平台验证。
- 运行成本：在相同机器和固定样本下测 OCR、分组、翻译、擦除、排版各阶段，报告失败率及耗时分布。

### 后续讨论重点

1. 先依据正常长度的英译中样本，确认错位、字号变化、错误换行和背景损坏分别来自哪一层；极端长译文只作边界测试。
2. 讨论正文是否保留源行位置，或在确认的段落区域内重排；菜单和按钮的单行约束应单独处理。
3. 明确格式保留的范围：位置、对齐、字号层级和行距之外，字体家族、粗细及行内样式需要保留到什么程度。

已确认：英译中为主要场景，必要时可以小幅缩字号。当前优先级是避免不必要的缩字、恢复正确的行与段落约束、检查对齐和显示比例，而非继续围绕罕见溢出设计交互。此记录更新研究结论，不代表已获实施授权。
