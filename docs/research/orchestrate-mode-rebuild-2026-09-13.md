# Orchestrate 模式重建调查

调查日期：2026-09-13。本次先研究模式定位和接口，不修改生产代码。外部资料均实际打开原文；官方文档按调查日页面理解，不保证其他版本行为一致。

## 结论

建议把 Orchestrate 重新定义为**主代理主动组织并行工作，并亲自推进主线**。它与普通模式的差别是主动寻找适合委派的工作，而不是增加另一套执行引擎、固定步骤或代理数量要求。

主代理仍负责理解用户目标、选择分工、途中调节和最终回答。子代理围绕明确范围工作，把实际发现和输出交回来。输出直接作为信息使用，不引入“失败／未完成”任务分类、验收、评分或回答放行。以上是本产品约束与设计建议，不是外部文档对所有多代理系统的统一规定。

这些来源不证明“主代理必须完全停手”，也不证明“多开代理一定更快”。产品需要的是主代理可随情况选择动作，而不是照搬某个上游系统的完整工作流。

## 重建后的最小行为

1. 找到能独立推进且有实际收益的工作时，主动委派；可并行的连续派出，自己继续推进其余主线。
2. 派工只说明目标、必要上下文和范围；涉及修改时说明文件归属，不扩大用户任务。
3. 相关追问优先联系原代理；根据实际进展收窄或调整方向，只等当前需要的对象。
4. 直接使用返回内容，必要时继续读取或追问；汇总分清来源和疑问，由主代理决定后续与回答。

“优先复用”不是把无关新任务都塞给旧代理。只有相关上下文有帮助时才继续；独立问题仍可新建。主代理收到某分支的运行事件后自行调整，其他独立分支继续推进。

## 精简提示方向（研究草案）

> 主动把适合独立推进的工作交给子代理并行处理，你同时推进主线。派工简明，交代目标、必要上下文和范围，避免重复调查或同时修改同一文件。根据进展调整方向，相关追问优先联系原代理，只等待当前需要的结果。结合实际输出回答，分清来源和疑问；简单或紧密依赖的工作直接自己处理。

这段只定义模式行为。`get`、`message`、`continue`、`wait` 的参数和分页方式应由现有工具说明提供，模式提示不再复制长篇操作手册。也不新增强制 Todo、固定角色模板或规定人数。

## 运行约束与内容判决的边界

保留现有并发容量、权限边界、用户停止、消息归属和分页等运行事实；它们使已有工具可用。容量不是要求必须占满的目标，等待超时不是对输出的评价。不要把此模式绑定额外的最低轮数、自动验收或必须所有代理结束才能回答的条件。

研发时可以观察重复调查、串行派工、上下文消耗、误述来源等现象；这是改进模式的线下依据，不进入线上给每份输出判分或阻止回答的流程。

| `goal.rs` / `reply.rs` 排除了 Orchestrate 中的 Goal；`commands/send.rs` 将多模型回答限定于 Act。`commands/mutations.rs` 把 Orchestrate 的换模型限制也称作“规划模式”。 | 这些是旁路兼容问题，应明确梳理；本次模式重建不直接开启 Goal 或多模型回答。若保留换模型限制，提示应准确描述实际模式。 |
| `plan.rs` 的模式提示测试仅检查关键词；`commands/tests.rs` 的预算测试重复一个抬高轮数的闭包。 | 实施时用实际模式组装与控制行为覆盖关键路径，移除只维护旧规则的断言；不增加运行中的回答拦截。 |

替换核心是旧模式提示及其额外预算规则。现有按 ID 读取、发送消息、继续、等待、停止，以及结果分页、运行时间和进度展示，继续作为主代理可以选用的能力。强制 Todo 的模式要求删除后，通用 Todo 工具是否使用仍由任务本身决定。

## 后续观察场景

- 简单单文件改动：主代理直接处理，不为展示模式额外派工。
- 多个独立调查方向：子代理同时推进，主代理也做独立工作。
- 途中修改某个分支要求：只联系该 ID，其他分支继续。
- 相关追问：原代理保留上下文继续；长结果按需续读。
- 多处代码修改：主代理与子代理划分文件，避免互相覆盖。
- 某分支返回没有发现或接口诊断：主代理根据事实调整，其他分支不被连带停止。

这些是实施后的观察案例，不是对模型最终回答新增的放行条件。
